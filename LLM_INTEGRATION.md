# Ритм — контракт интеграции произвольной LLM

**Версия:** 1.2 · **Статус:** готовый порт; реальная модель не подключена.

Задача этого слоя — **обрабатывать весь жизненный цикл диалога, БД и tools без зависимости от модели**. Другой разработчик реализует только два метода `LLMProvider`.

## Поток запросов

```text
web/app.js -> POST /api/chat -> ChatRouter
                              |
                              +-- pending? -> обработать уточнение/подтверждение
                              |
                              +-- RuleDialogue -> понятная команда -> Planner -> SQLite
                              |
                              +-- неизвестная команда -> LLMProvider.interpret()
                                                        |
                                                        v
                                                ParsedCommand
                                                        |
                                                        v
                                             ToolRegistry -> Planner -> SQLite
                                                        |
                                                        +-- при пустом поиске:
                                                        LLMProvider.expand_search()
                                                        -> Planner.search() -> SQLite
```

Подключение LLM **не даёт** доступа к SQLite, SQL, произвольному Python-коду или файловой системе.

## Интерфейс

См. `assistant/llm_provider.py`:

```python
class LLMProvider(Protocol):
    def interpret(self, text: str, context: LLMContext, tools: list[dict]) -> ParsedCommand: ...
    def expand_search(self, query: str, context: LLMContext) -> list[str]: ...
```

`interpret` получает исходный текст **отдельным аргументом**, JSON-контекст **только с `now` и IANA `timezone`**, и шесть статических JSON Schema инструментов того же формата, что `/api/tools`. Модель должна выбрать инструмент и предложить параметры согласно его JSON Schema. **`interpret` не выполняет операцию.**

`expand_search` вызывается только если первичный поиск пуст. Возвращает до пяти поисковых запросов на естественном языке; не SQL. Повторный поиск, лимиты, дедупликация, хранение данных и проверка ошибок полностью на стороне бэкенда.

## Неподвижные инструменты и контекст времени

**Список инструментов статический** и зарегистрирован в `assistant/tools.py` (`DEFINITIONS`). Модель может выбрать только `create_event`, `list_events`, `search_events`, `get_event`, `update_event`, `cancel_event` или `unknown`. На лету создавать tools, выполнять произвольный код или SQL нельзя.

**JSON-контекст модели состоит ровно из двух полей:**

```json
{
  "now": "2026-10-31T10:38:00+03:00",
  "timezone": "Europe/Moscow"
}
```

Значение `now` генерируется сервером при обращении, имеет явное UTC-смещение и соответствует IANA timezone. Пример времени условный. `session_id`, `active_event_id`, история сообщений, данные БД и произвольные дополнительные поля в `LLMContext` **не включаются**. Это ограничение именно JSON-контекста; текст запроса и статический каталог tools передаются в `interpret` отдельно. Если интегратору требуется история, это изменение контракта нужно согласовать отдельно.

**Выход из модели — JSON-команда, не SQL:**

```json
{"tool": "search_events", "arguments": {"query": "обсуждение зарплаты"}}
```

`ParsedCommand` запрещает лишние верхнеуровневые поля; конкретный тип аргументов **каждого вызова** отдельно валидируется строгой Pydantic-схемой в `ToolRegistry.execute()`. Поля вроде `sql`, `query_sql`, `confirm` или незарегистрированные функции будут отклонены. Все SQL-операции выполняются только параметризованным кодом внутри сервиса и SQLite-слоя.

**Отмена — отдельная транзакция подтверждения:** `cancel_event` без специального серверного `confirmed_by_user` не выполняется. Этот флаг **никогда не читается из JSON модели**; диалог сначала выдаёт запрос подтверждения, сохраняет `pending_action=confirm_cancel`, затем ожидает отдельное сообщение пользователя «да» / «нет». Запоминается версия события — если запись изменится до ответа, отмена будет отклонена. Прямой `DELETE /api/events/{id}` и обход через `PATCH status=cancelled` запрещены (409). Для HTTP/UI сначала `POST /api/events/{id}/cancel-request` с `{"session_id":"..."}`, затем отдельный `POST /api/chat` с `{"session_id":"...","message":"да"}` или `нет`. Кнопка веб-интерфейса использует эту двухшаговую процедуру.

### Возвращаемая структура

```json
{
  "tool": "create_event",
  "arguments": {
    "kind": "meeting",
    "title": "Созвон с командой",
    "scheduled_date": "2026-11-04",
    "scheduled_time": "15:00"
  },
  "target_query": null
}
```

Поле `tool` — одно из `create_event`, `list_events`, `search_events`, `get_event`, `update_event`, `cancel_event`, `unknown`. Поле `target_query` используется для поиска события перед `get_event`, `update_event` или `cancel_event`, **если у модели нет реального `event_id`**:

```json
{
  "tool": "update_event",
  "arguments": {"status": "done"},
  "target_query": "отчёт Ивану"
}
```

Если найдено несколько подходящих событий, **бэкенд спросит пользователя**, какое выбрать, сохранит варианты в `sessions` и обработает ответ «вторую» или «#15» без второго обращения к модели.

Если для создания встречи/напоминания отсутствует название, дата или время, бэкенд задаст последовательные уточняющие вопросы. Он также самостоятельно подтверждает отмену и проверяет версию записи перед отменой.

### Пример провайдера без привязки к модели

```python
from assistant.api import create_app
from assistant.contracts import ParsedCommand

class MyProvider:
    def interpret(self, text, context, tools):
        # Здесь интегратор сам вызывает любую выбранную модель.
        # Ниже ТОЛЬКО заглушка с фиксированным ответом:
        return ParsedCommand(tool="list_events", arguments={})

    def expand_search(self, query, context):
        return []

app = create_app(llm_provider=MyProvider())
```

Для использования в отдельном запускном файле:

```python
# run_with_llm.py (создаётся разработчиком модели)
from assistant.api import create_app
from my_provider import MyProvider
app = create_app(llm_provider=MyProvider())
```

Затем: `uvicorn run_with_llm:app --host 127.0.0.1 --port 8000`. В репозитории **нет** реального `my_provider`, он добавляется интегратором.

Если провайдер отсутствует, используется `NullLLMProvider`; правила и все REST-методы продолжают работать. При недоступности модели свободная формулировка получает понятный отказ, без ложной фиксации действия.

## Требования к интегратору

1. Не возвращать SQL, Python или shell-команды: только JSON-объект `ParsedCommand`; аргументы tools строго по опубликованным JSON Schema.
2. Не придумывать `event_id` — получать из контекста, ранее найденных записей либо использовать `target_query`.
3. Передавать `arguments` согласно `/api/tools` (JSON Schema). Дополнительные поля запрещены.
4. Не считать успех гарантированным: ответы об ошибке или конфликте формирует бэкенд по фактическому результату `ToolRegistry`.
5. Не обходить уточняющие вопросы и подтверждение отмены.
6. Соблюдать тайм-ауты и лимиты своей модели; исключения из `interpret` переводятся в контролируемый ответ.
7. `LLMProvider` синхронный: это соответствует текущему `def` endpoint в FastAPI, работающему в threadpool. Если потребуется асинхронный SDK, обёртку надо реализовать без вызова `asyncio.run()` внутри действующего цикла.
8. Контекст может содержать пользовательские данные и тексты задач; выбор облачной модели требует отдельного решения по приватности.

## Известные ограничения

- Rule-based обработчик остался существующим и может распознавать неоднозначные формулировки как определённую команду. При успешном совпадении LLM не вызывается. Дополнительное повышение точности правил — отдельная задача.
- Автоматических Windows-уведомлений, локального Whisper/Silero и реальной LLM в этой версии нет.
- Список инструментов остаётся из шести операций: создание, список, поиск, получение, обновление, отмена.
- Для существующего `RuleDialogue` сохранились его отдельные уточнения при создании; новые состояния LLM используют `pending_action` = `complete_command`, `select_event`, `confirm_cancel`.
- Для уже реализованных инструментов результат — `ChatOutput`, а не произвольный ответ модели.
- Лексический/fuzzy поиск пока перебирает заголовки; синонимы добавляются провайдером. Векторная база не используется.
- Синхронный `ChatRouter` не сериализует параллельные запросы одного `session_id`; для многопользовательского production-развёртывания нужна дисциплина конкурентного доступа к сессиям.
