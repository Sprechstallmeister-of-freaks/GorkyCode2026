# Архитектура: DeepSeek provider и независимое ядро

## Границы ответственности

**Planner** — единственный источник бизнес-правил. Не читает промпты и не зависит от LLM или Web Speech API. Вход: валидированные сущности `EventCreate`, `EventPatch`; выход: `Event` или типизированная доменная ошибка. Транзакции защищают от конкурентного создания пересекающихся встреч.

**ToolRegistry** — единственный шлюз из диалога в Planner: `specs()` отдаёт шесть структур `type=function` с JSON Schema, `execute(name, args)` повторно валидирует аргументы и вызывает Planner. Инструментов сырого SQL, файловой системы или выполнения Python нет. `cancel_event` требует серверный `confirmed_by_user=True`, который модель не может передать через аргументы.

**ChatRouter** — единая точка оркестрации. Сначала использует `RuleDialogue`; незнакомую формулировку передаёт `LLMProvider`. Реализует pending-состояния, последовательные уточнения, выбор записи из нескольких совпадений, подтверждение отмены и закрепление `expected_version`.

**DeepSeekClient / DeepSeekProvider** — OpenAI-совместимый HTTP-клиент и реализация model-neutral границы. Провайдер переводит один tool call в `ParsedCommand`, но сам не выполняет инструменты. Ключи загружаются из окружения или игнорируемого `.env` и не возвращаются через API. Пул `DEEPSEEK_API_KEYS` переключается при auth/quota ошибках; cooldown 429 и блокировки слотов потокобезопасны. Дополнительный `describe()` может описать фактический read-only результат.

**RuleDialogue** — рабочий детерминированный fallback. Поддерживаемые команды выполняются без API-ключа. Ручной REST/UI и Planner от него не зависят.

**SQLite** — локальное хранилище. `events` содержит тип, статус, срок, время, timezone, версию и source; `sessions` хранит активный ID и pending уточнение; `messages` — полную историю завершённых реплик.

## Протокол запроса

1. `ChatRouter` проверяет pending-состояние. Уточнения и подтверждения обрабатывает детерминированно, а каждое новое сообщение при настроенном провайдере сначала передаёт в `DeepSeekProvider.interpret()`.
2. Если модель недоступна или вернула `unknown`, включаются локальные правила. Если выбран валидный инструмент, `ToolRegistry`/Planner выполняют его без повторной обработки через fallback.
3. Провайдер передаёт текущие `now` + IANA timezone, исходный текст и статические JSON Schema в `/chat/completions` с `tool_choice=auto`. По умолчанию используется LiteRouter и модель `deepseek-v4.1-flash-1017:free`.
4. Провайдер принимает не более одного tool call, проверяет JSON и имя инструмента и возвращает `ParsedCommand`. `target_query` позволяет серверу самому найти ID записи; модель не обязана его знать.
5. `ToolRegistry` повторно проверяет аргументы через Pydantic. Только после этого Planner выполняет операцию. Конфликты и бизнес-правила всегда проверяет сервер.
6. Для create/update/cancel сервер формирует подтверждение по фактическому результату. Для list/search/get модель может кратко описать результат; при ошибке описания детерминированный ответ с данными сохраняется.
7. При пустом поиске `expand_search()` может вернуть до пяти синонимов. Повторный поиск и дедупликация выполняются сервером.
8. Ошибки DeepSeek не приводят к повторному выполнению мутации: провайдер только предлагает команду, а выполнение начинается после успешной валидации. Неподдержанная свободная фраза получает контролируемый отказ.

## Безопасная отмена

Диалоговая и HTTP-отмена используют один pending-протокол. Сервер сначала сохраняет `confirm_cancel` и текущую версию записи, затем ожидает отдельное «да»/«нет». Изменение версии до подтверждения приводит к конфликту. Прямой `DELETE` и `PATCH status=cancelled` запрещены; попытка отменить через `update_event` также отклоняется. Для всех pending-сценариев действует guard: два ответа без новых полезных данных завершают сценарий без применения изменений, поэтому неформальные ответы не создают бесконечный цикл уточнений.

## Контекст и compaction

`LLMContext` намеренно содержит только `now` и `timezone`. `session_id`, история и активный ID не отправляются как метаданные модели. Рабочая память остаётся на сервере в `sessions`; `target_query` и pending-состояния связывают шаги без передачи полной истории в DeepSeek.

* **Истина**: `events`, а не ответ модели или summary.
* **Working memory**: `sessions.active_event_id` и `sessions.pending_*`.
* **History**: исходные завершённые реплики остаются в `messages`, но текущему провайдеру не передаются.
* **Summary/compaction**: отдельная таблица и summarization пока не реализованы.

## Голос

Browser SpeechRecognition возвращает текст, после ручной отправки вызывается `POST /api/chat`; ответ может озвучиваться speechSynthesis. Голосовой сценарий в этой итерации не менялся. Browser SpeechRecognition не гарантирует офлайн-работу.

## Принятые решения

* SQLite вместо Postgres: один локальный пользователь, простой запуск без инфраструктуры.
* FastAPI/Pydantic: строгие схемы, OpenAPI и проверяемость.
* LLM-first + локальный резерв: модель обрабатывает все новые сообщения, а правила сохраняют работоспособность при её сбое или отсутствии ключа.
* Vanilla JS: UI не требует сборки.
* Search без embeddings: доступность без GPU; синонимы LLM — отдельный необязательный слой.
* Soft cancel, отдельное подтверждение и оптимистичные версии для защиты данных.

## Что улучшать перед публичным размещением

Аутентификация, разделение пользователей, CSRF/лимиты, HTTPS, CORS, наблюдаемость, защита персональных данных, миграции, резервные копии и queue уведомлений. Прототип **не предназначен для прямого публичного доступа** без этих мер.
