# Архитектура и следующий этап: LLM adapter

## Границы ответственности

**Planner** — единственный источник бизнес-правил. Не читает промпты, не импортирует Ollama, не зависит от Web Speech API. Вход: валидированные сущности `EventCreate`, `EventPatch`; выход: `Event` или типизированная доменная ошибка. Транзакции защищают от конкурентного создания пересекающихся встреч.

**ToolRegistry** — шлюз для будущей LLM: `specs()` отдаёт структуры `type=function` с JSON Schema, `execute(name, args)` валидирует и вызывает Planner. Не предоставлять инструмент сырого SQL или выполнения Python. `cancel_event` не доверяет аргументам модели: исполнитель требует отдельный серверный флаг `confirmed_by_user=True`, установленный после подтверждения в UI. Модель не может установить его через tool arguments.

**RuleDialogue** — только временная демонстрация без LLM. Его можно удалить, когда появится интерпретатор запросов; API и Planner останутся неизменными.

**SQLite** — устойчивое локальное хранилище. `events` содержит тип, статус, срок, время, timezone, версию и source; `sessions` хранит активный ID и pending уточнение; `messages` — полную историю сообщений. У нас пока нет отдельной таблицы summary.

## Предлагаемый протокол LLM

1. Собрать системную инструкцию, дату/время (`now` + IANA timezone), список доступных инструментов и **последние завершённые** сообщения.
2. Вызвать Ollama с моделью, способной на tool calling.
3. Проверить аргументы выбранного tool с Pydantic; вызвать `ToolRegistry.execute` и сохранить исходный вызов + ответ инструмента в историю.
4. Вернуть результат модели, если нужен следующий шаг, или детерминированно подтвердить факт результата пользователю.
5. Установить максимальное число шагов агента, дедлайн запроса, явное подтверждение удаления, политику повторов и журнал ошибок.

Не стоит доверять модели разрешение конфликтов или проверку даты: это всегда выполняет Planner. Модель должна только решить, *какую операцию запросить*.

## Контекст и compaction

Мы не добавляем в текущий проект пустую имитацию памяти LLM. Но база уже содержит все факты для её реальной реализации.

* **Истина**: `events` (не summary).
* **Working memory**: `sessions.active_event_id` и `sessions.pending_*` (не суммаризировать).
* **Recent window**: последние N завершённых циклов «user → assistant/tool → result».
* **Summary**: отдельно сохранённая сводка старых сообщений; обновлять только когда токены превысили порог, не при каждом сообщении.
* **Retrieval**: выборка оригинальных сообщений из `messages` при необходимости.

Рекомендация: хранить исходную историю без удаления, делать summarization асинхронно только когда есть надёжный вызов модели, не обрывать инструментальную цепочку посреди compaction. Предупреждение: без LLM это пока план, а не реализованный механизм.

## Голос

Сегодня browser SpeechRecognition возвращает текст, затем вызывается `POST /api/chat`, ответ озвучивает speechSynthesis. При необходимости полностью офлайн-режима заменить только слой ASR/TTS, оставив Planner и инструменты без изменений. Browser SpeechRecognition не гарантированно работает без интернета.

## Принятые решения

* SQLite вместо Postgres: один локальный пользователь, лёгкий запуск без серверной инфраструктуры.
* FastAPI/Pydantic вместо собственного HTTP+JSON: строгие схемы, OpenAPI, тестируемость.
* Vanilla JS вместо SPA-framework: тестовое задание оценивает логику, UI не требует сборки.
* Search без embeddings: доступность без GPU и объективная проверяемость; семантический слой можно подключить отдельно.
* Отмена вместо безвозвратного DELETE, версия для оптимистичных обновлений, проверка временных конфликтов.

## Что улучшать перед публичным размещением

Аутентификация, разделение данных между пользователями, CSRF/лимиты запросов, HTTPS, настройка CORS, логи/наблюдаемость, защита личных данных, миграции для будущих версий, резервное копирование, async jobs и queue для уведомлений. Прототип **не предназначен для прямого публичного доступа**.
